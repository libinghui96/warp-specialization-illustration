TMA · MMA · Warp Specialization：设计理念与效果

GPU 上的矩阵乘由 Tensor Core（专门做矩阵乘的硬件单元）完成。它越来越快之后，瓶颈变成了“怎么把数据及时喂给它”。 下面三项技术都在解决这个问题。本页用同一个 GEMM（C = A·Bᵀ，FP16 输入、FP32 累加，tile 128×128×64）在 RTX 5080 上的实测数据，以及为 H100、B200 编译出的汇编来说明。 5080 只支持 WS 所需部件的一部分，它的实测数字只能当作下限，原因见第 2 节。

TMA Tensor Memory Accelerator

Warp Specialization 简称 WS

线程分角色：有的只搬数据，有的只计算，彼此用 mbarrier 握手。

+6.5%

5080 实测，只含三种架构共有的那部分机制，是下限（见第 2 节）

名词：warp = 32 个线程，GPU 的最小调度单位；warpgroup = 4 个 warp；CTA（block）= 一个线程块，这里负责一个 128×128 的输出 tile； k-tile = 沿 K 方向切出的一段（64 列）输入数据，一个 tile 要依次处理很多个 k-tile。

1. 5080 上的实测结果

所有版本的计算代码和 tile 尺寸完全一样，只有“谁搬数据、怎么同步”不同。结果都和 cuBLAS 逐元素比对过。

单位 TFLOPS，越高越好。“WS，但用 cp.async 搬”比不分工还慢：让 1 个 warp 发出整个 tile 的拷贝指令，指令数反而更多，所以 WS 要和 TMA 一起用。 “不重叠 ×2 block”是每个 SM 上同时驻留两个 block，一个搬时另一个算，等于 block 之间互相掩盖。

2. 5080 的结果能说明什么，不能说明什么

5080 只支持 WS 所需部件的一部分。第 1 节的 +6.5% 测到的是三种架构共有的那部分机制：producer 用 TMA 搬数据，用 mbarrier 握手取代全体同步。 H100 和 B200 上 WS 更主要的价值来自异步矩阵乘和 TMEM，5080 没有这些，所以这个数字只能当作下限，不能代表后两者。

为什么 5080 上的数字偏小

  • 计算线程仍被同步指令占着。每个 k-tile 的 192 条 ldmatrix 和 512 条 mma.sync 一条不少，WS 只省掉了搬数据和全体同步那部分。
  • 硬件上限低，可回收的空间小。最好的版本和 cuBLAS 都停在约 110 TFLOPS，Tensor Core 利用率约 48%。在 4096 和 8192 规模下，不分工的 TMA 版本已经达到 cuBLAS 的 92%～94%。
  • 流水只能放 3 级。shared memory 不到 H100 的一半。

它能说明的

  • 共有的机制确实有效：等全体同步的 warp 数从 1.72 降到 0.01，速度 +6.5%。
  • WS 必须配合 TMA：用 cp.async 搬的 WS 比不分工还略慢（最多约 1%）。
  • setmaxnreg 确实能把寄存器让出来：大 tile 上 +3%～9%。

它不能说明的

  • H100 上异步 wgmma 带来的收益，包括两组 warpgroup 交替做矩阵乘和其他计算。
  • B200 上搬、发指令、写回三个角色分工的收益。
  • 多个 CTA 共享一次加载的收益。

3. 三个设计理念

TMA：搬数据交给硬件

要解决的问题
以前每个线程自己算地址、发 cp.async。搬一个 tile 要上百条指令，占用的正是本该去计算的线程。
做法
主机端用 tensor map 描述张量的形状和布局；设备端 1 个线程给出坐标，硬件完成地址计算、swizzle 和拷贝，写完后自动通知 mbarrier。
预期效果
指令数下降；搬数据不再占用计算线程；1 个线程就能当 producer，这是 WS 的前提。
证据 5080 实测
4096 规模下执行的指令数：不分工 148.6M → 122.0M；WS 下 178.1M → 113.3M。速度 +4%。

MMA：一条指令算更大的块

要解决的问题
mma.sync 一次只算 16×8×16，操作数要先用 ldmatrix 读进寄存器，累加器也占寄存器。Tensor Core 变快后，发指令本身成了开销。
做法
H100 的 wgmma：4 个 warp 合发一条 64×N×16 的异步指令，操作数用描述符直接从 shared memory 读。 B200 的 tcgen05：1 个线程发指令，累加器放进专用的 TMEM。
预期效果
指令数降两个数量级；线程发完指令就空出来；寄存器压力逐代下降。
证据 编译 + 反汇编
每个 k-tile 的指令数 704 → 8 → 4，每线程寄存器 132 / 168 / 70。H100、B200 的速度没有测过。

WS：搬和算分开，各干各的

要解决的问题
所有 warp 干同样的事时，每个 k-tile 都要全体同步一次，最慢的 warp 拖住整个 block；每个 warp 还都背着搬和算两套开销。
做法
producer 只搬，consumer 只算。每块缓冲配一对 mbarrier：full（数据到了）和 empty（用完了），一对一握手，取代全体同步。 setmaxnreg 把 producer 用不到的寄存器让给 consumer。
预期效果
搬和算持续重叠，Tensor Core 少空转；没有 block 级同步；对访存延迟更不敏感。
证据 5080 实测
速度 +6.5%；等同步的 warp 数 1.72 → 0.01；Tensor Core 利用率 45.1% → 48.5%。setmaxnreg 在大 tile 上再 +3%～9%。这是下限，见第 2 节。

6. 哪些是测出来的，哪些不是



  
结论依据说明

  
5080 支持哪些 WS 部件实测TMA、mbarrier、setmaxnreg 实际运行过；2 个 CTA 的 cluster 能启动；wgmma、tcgen05 被编译器拒绝。

  
5080 上各版本的速度和增量实测同一 kernel 只改搬运和同步方式；结果逐元素对过 cuBLAS。

  
5080 上的指令数、同步停顿、Tensor Core 利用率实测Nsight Compute，4096 规模。采集时 TMA 的写法还没改成最终版，数值可能略有出入。

  
三种架构的指令条数、寄存器数编译 + 反汇编本机 CUDA 12.9 编译三个目标后用 cuobjdump 统计。

  
H100、B200 用例能算对、能跑多快未验证本机只有 5080，这两份代码没有运行过。描述符编码照 CUTLASS 和 DeepGEMM 写。

  
H200 上 WS 更能掩盖访存延迟仿真，旁证Accel-Sim 里把 DRAM 延迟加倍：非 WS 的 kernel 慢 33%～37%，WS 的 FP8 GEMM 慢 16%～23%。
    但两者不是同一个 kernel，仿真误差 1%～29%，只能说明方向。

  
setmaxnreg 在 H100 上的收益无数据模拟器把它当空操作；5080 上实测大 tile +3%～9%。
