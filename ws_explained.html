TMA · MMA · Warp Specialization：设计理念与效果

GPU 上的矩阵乘由 Tensor Core（专门做矩阵乘的硬件单元）完成。它越来越快之后，瓶颈变成了“怎么把数据及时喂给它”。 Warp specialization（下文简称 WS）的做法是：把一个线程块里的线程分成不同角色，有的只负责搬数据，有的只负责计算，中间用几块缓冲接力，让搬和算同时进行。 本页用一个具体的矩阵乘例子，一步步说明数据怎么取、怎么算、线程怎么分工、流水怎么掩盖访存延迟，以及 RTX 5080、H100、B200 三种架构的差别。

TMA Tensor Memory Accelerator

把“搬一整块数据”做成一条指令，交给硬件拷贝引擎。

2 条指令

一个线程搬完一个 k-tile 的 A 和 B（共 32 KB）

MMA 矩阵乘加指令的三代演进

一条指令算得更大，操作数和累加器逐步离开寄存器。

704 → 8 → 4

每个 k-tile 发出的指令数：5080 / H100 / B200

Warp Specialization WS

线程分角色，用成对的信号一对一握手，不再全体同步。

0 次

每个 k-tile 需要的全体同步次数（不分工时是 1～2 次）

名词：warp = 32 个线程，GPU 的最小调度单位；warpgroup = 4 个 warp；CTA = 一个线程块；shared memory = CTA 内部的高速缓冲区； mbarrier = 放在 shared memory 里的同步信号，等的人不用和其他线程一起停下来。

1. 例子：有哪些数据，怎么取

要算的是 C = A·Bᵀ，也就是 C[m][n] = Σk A[m][k] · B[n][k]。A、B、C 都是 4096×4096，A 和 B 是 FP16，C 是 FP32。任务这样拆：

  • 按输出拆。C 切成 32×32 个 128×128 的 tile，每个 tile 交给一个 CTA，1024 个 CTA 同时运行。

4. 流水掩盖：怎么实现，有什么效果


从显存取一块数据要等一段时间（访存延迟）。如果取一块、算一块，Tensor Core 就要在每次取数据时空等。流水的做法是多准备几块缓冲，提前把后面的数据取回来：
算第 kt 块时，第 kt+1、kt+2 块已经在路上。只要数据到达得比计算消耗得快，延迟就被“掩盖”了，Tensor Core 感觉不到。


实现上就是第 2 节那两个循环加一对信号：producer 一看到 empty[s] 就发下一次搬运，不等数据回来；consumer 只等 full[s]。下面的模拟器按这个规则推演 12 个 k-tile，可以调访存延迟和缓冲块数。

TMA：H100 和 B200 的不同


基本用法两边一样：一个线程给出坐标，硬件搬一整块，搬完通知 mbarrier。本页三个用例的 TMA 代码完全相同。差别在周边：

6. 设计理念小结



  

    
TMA：搬数据交给硬件

    

      
要解决的问题

      
以前每个线程自己算地址、发 cp.async。搬一个 tile 要上百条指令，占用的正是本该去计算的线程。

      
做法

      
主机端用 tensor map 描述张量；设备端 1 个线程给出坐标，硬件完成地址计算、swizzle 和拷贝，写完后自动通知 mbarrier。

      
预期效果

      
指令数下降；搬数据不再占用计算线程；1 个线程就能当 producer，这是 WS 的前提。

    

  

  

    
MMA：一条指令算更大的块

    

      
要解决的问题

      
mma.sync 一次只算 16×8×16，操作数要先读进寄存器，累加器也占寄存器。Tensor Core 变快后，发指令本身成了开销。

      
做法

      
H100 的 wgmma：4 个 warp 合发一条异步指令，操作数直接从 shared memory 读。B200 的 tcgen05：1 个线程发指令，累加器放进 TMEM。

      
预期效果

      
指令数降两个数量级；线程发完指令就空出来；寄存器压力逐代下降。

    

  

  

    
WS：搬和算分开，各干各的

    

      
要解决的问题

      
所有 warp 干同样的事时，每个 k-tile 都要全体同步一次，最慢的 warp 拖住整个 CTA；每个 warp 还都背着搬和算两套开销。

      
做法

      
producer 只搬，consumer 只算，用 full / empty 一对信号握手。setmaxnreg 把 producer 用不到的寄存器让给 consumer。

      
预期效果

      
搬和算持续重叠，Tensor Core 少空转；没有 CTA 级的同步；对访存延迟更不敏感。

各种做法的速度


所有版本的计算代码和 tile 尺寸完全一样，只有“谁搬数据、怎么同步”不同。结果都和 cuBLAS 逐元素比对过。





  

  




单位 TFLOPS，越高越好。“WS，但用 cp.async 搬”比不分工还略慢：让 1 个 warp 发出整个 tile 的拷贝指令，指令数反而更多，所以 WS 要和 TMA 一起用。
“不重叠 ×2 block”是每个 SM 上同时驻留两个 CTA，一个搬时另一个算，等于 CTA 之间互相掩盖。



  
为什么 5080 上的数字偏小

    
    
      
  • 计算线程仍被同步指令占着。每个 k-tile 的 192 条 ldmatrix 和 512 条 mma.sync 一条不少，WS 只省掉了搬数据和全体同步那部分。
    • 
      
  • 硬件上限低，可回收的空间小。最好的版本和 cuBLAS 都停在约 110 TFLOPS。在 4096 和 8192 规模下，不分工的 TMA 版本已经达到 cuBLAS 的 92%～94%。
    • 
      
  • 缓冲只能放 3 块。shared memory 不到 H100 的一半。
    • 
    

  
它能说明的

    
    
      
  • 共有的机制确实有效：等全体同步的 warp 数从 1.72 降到 0.01，速度 +6.5%。
    • 
      
  • WS 必须配合 TMA：用 cp.async 搬的 WS 比不分工还略慢（最多约 1%）。
    • 
      
  • setmaxnreg 确实能把寄存器让出来：大 tile 上 +3%～9%。
    • 
    

  
它不能说明的

    
    
      
  • H100 上异步 wgmma 带来的收益，包括两组 warpgroup 交替做矩阵乘和其他计算。
    • 
      
  • B200 上搬、发指令、写回三个角色分工的收益。
    • 
      
  • 多个 CTA 共享一次加载的收益。

第 5 节里 H100 和 B200 的异步矩阵乘、TMA 的差别读源码依据指令的语义和 CUTLASS、DeepGEMM 的源码，没有在真机上运行。wgmma 只被 sm_90a 接受、tcgen05 只被 sm_100a 接受是本机编译确认的。重叠的时间线是示意图。

  
第 4 节的流水模拟器简化模型按 kernel 里的握手规则推演，用来说明原理，不是测量结果。

  
H200 上 WS 更能掩盖访存延迟仿真，旁证Accel-Sim 里把访存延迟加倍后比较变慢的幅度。两个 kernel 不是同一个，仿真误差 1%～29%，只能说明方向。

  
setmaxnreg 在 H100 上的收益无数据模拟器把它当空操作；5080 上实测大 tile +3%～9%。
